## 执行节奏与完成标准

- 按批次顺序执行；一次只开发一个闭环，真实浏览器操作串行进行，不同时启动多条编辑器任务。
- 每批包含：读取实际能力、回归测试先行、实现、定向测试、真实样本复核、更新本页。不会因没有 HTTP API 就直接判定不可实现。
- 页面能力依次选择现有 API、稳定页面 façade、真实菜单交互。菜单交互也必须明确目标、检查可编辑权限、等待保存、重新读取结果。
- 修改后验失败先只读复核，不重放新增记录、复制页面、评论或答卷。
- 不新增依赖；不自动发布 npm/GitHub 版本。构建版本与已发布版本、代码通过与线上通过分开记录。

## 批次 2：内置浏览器与 CLI 的宿主接入

目标是 Agent 在同一授权身份下使用内置浏览器，减少重复登录。CLI 不能自行操纵所有宿主的 cookie 容器，需要明确宿主能力边界。

1. 区分三种能力：宿主已验证同账号、宿主支持安全会话导入、宿主只支持打开 URL。
2. 已有 `session import/export/watch` 作为受控宿主适配边界。会话文件仅由适配程序读取，不进入模型上下文或聊天；不得用 `document.cookie` 代替 HttpOnly cookie 导入。
3. 支持导入的宿主：按相同 origin 导入 cookie，随后在宿主中验证账号及目标，再声明 `sessionShared:true`；不得仅凭导出成功声明接入完成。
4. 仅支持 URL 的宿主：提供截图/导出物和明确的会话状态，不能承诺自动登录。需要宿主插件接口时将接口、失败状态与验证步骤写清。
5. 验证同账号、账号不一致、过期、不同 origin、宿主能力缺失、会话撤销；不以本机隔离 Chrome 测试冒充内置浏览器验收。

## 批次 3：补齐表格页面能力，每项独立交付

按以下顺序，每项先限定可验收范围，再扩展：

1. 排序：显式范围、表头、方向及数据类型；通过重开/导出核对行记录关联和非目标区域。
2. 数据验证：先做列表、数字与日期；菜单配置后重开规则，并分别验证合法/非法输入；不把批注当验证规则。
3. 单元格格式：数值格式、字号、对齐、边框、行高列宽分项支持，导出核对属性及范围。
4. 清洗：去重、分列、填充分别实现；操作前输出影响范围，保留原行标识和数据差异，避免仅在本地另建文件。
5. 透视表：明确源范围、输出位置、行列维度和聚合；菜单生成后独立计算预期汇总，检查源数据未改变。
6. 评论：先做指定单元格、纯文本、不提及他人的评论创建与读取定位；保存后核对作者、正文和锚点，再扩展其他套件。评论与单元格批注分别建模。

瓶颈是当前前端 façade 的参数语义、目标选择和读回核验尚未稳定，不是浏览器路线不可行。每项应继续调查真实菜单，而非只增加“unsupported”的说明。
